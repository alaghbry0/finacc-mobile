   123→## 1. مقدمة الوثيقة
   124→
   125→### 1.1 الغرض
   126→
   127→توثّق هذه الوثيقة المتطلبات الوظيفية وغير الوظيفية، ومعمارية النظام، ونموذج البيانات، ومواصفات التصميم لتطبيق محاسبي عربي متكامل يُبنى من الصفر بواسطة **React Native + Expo**. الوثيقة مكتوبة بحيث تصلح مرجعاً مباشراً للمطوّر (أو لفريق تطوير أو وكيل ذكاء اصطناعي) دون حاجة لأي مستند إضافي: كل ميزة لها رقم متطلب قابل للتتبّع، وكل جدول قاعدة بيانات له مخطط SQL كامل، وكل شاشة لها وصف تفصيلي.
   128→
   129→**طبيعة هذا الإصدار (v1.2)**: هو إصدار التجميد الناتج عن مراجعة شاملة أجراها فريق مراجعة متخصص (مصمم UI/UX أول، محاسب قانوني CPA، مهندس جودة QA، مدير منتج PM) أنتجت 53 نتيجة و9 قرارات ملزمة — **كلها مدمجة في هذا النص**. لا يوجد أي قرار معلق: كل موضع كان «حسب الإعداد» أو «قابل للضبط» بلا تعريف أصبح له مفتاح موثق في سجل الإعدادات (ملحق هـ)، وكل تعارض بين الوثيقتين حُسم بقرار مسجل (ملاحق ز وط).
   130→
   131→### 1.2 النطاق
   132→
   133→يُبنى التطبيق كبديل شخصي كامل الوظائف عن تطبيق «المحاسب المالي | فواتير مبيعات» الشهير. **نطاق V1** (المجمد في هذا الإصدار) يشمل 14 وحدة: الفوترة (بيع/شراء/مرتجعات مرتبطة)، المخزون (مستودع واحد فاعلي)، العملاء والموردون، التقسيط (مخفّض)، الصناديق والنقدية (بمسحوبات المالك)، **الشيكات (تتبع مصغّر — وحدة جديدة)**، العملات متعددة (بفروق الصرف المحققة)، التقارير (بأرباح مصححة)، الطباعة والمشاركة (بسند مرقّم)، النسخ المحلي، الأمان (مدير + PIN)، الإعدادات وOnboarding.
   134→
   135→**مؤجل صراحة** (التفصيل والأسباب في ملحق ح): الموظفون/الحضور/الرواتب → V1.1؛ المناديب والعمولات → V2؛ عروض الأسعار → V1.1؛ الدفعات/التسلسلي FEFO وواجهة تحويل المخازن → V1.1/V1.2؛ النسخ السحابي Supabase → V1.1؛ SMS والصور المرفقة وQR الموقّع وHMAC والطابعات الشبكية → V2.
   136→
   137→**يُستثنى** من النطاق كلياً: كل ما يتعلق بالترخيص التجاري (اشتراكات، شراء داخل التطبيق، تفعيل باقات، ربط جهاز) — التطبيق للاستخدام الشخصي فقط.
   138→
   139→### 1.3 جمهور الوثيقة
   140→
   141→- **المطوّر المنفّذ** (أنت أو أي مطوّر/وكيل مستقبلي): كل أقسام الوثيقة — ويبدأ إلزامياً من القسم 0.
   142→- **أدوات التطوير المساندة بالذكاء الاصطناعي** (Cursor / Copilot / Claude): الوثيقة بصيغة Markdown قياسية تُغذّى مباشرة كمرجع سياق أثناء كتابة الكود، مع القسم 0 كقوانين عليا.
   143→
   144→### 1.4 اصطلاحات الترقيم
   145→
   146→- `FR-XX-YY`: متطلب وظيفي — XX رقم الوحدة، YY رقم المتطلب.
   147→- `NFR-XX`: متطلب غير وظيفي. — `DS-XX`: بند مواصفات تصميم. — `AC-XX`: معيار قبول.
   148→- كلمات الإلزام: **يجب** (إلزامي)، **ينبغي** (موصى به)، **يمكن** (اختياري).
   149→- **قاعدة صياغة ملزمة**: يُمنع استخدام عبارات «حسب الإعداد / قابل للضبط / لو مفعّل / اختياري» إلا بمرجع صريح لمفتاح في **سجل الإعدادات (ملحق هـ)** الذي يحدد المفتاح والقيمة الافتراضية والنطاق والدور المصرّح له بالتغيير.
   150→
   151→### 1.5 ملخص تنفيذي
   152→
   153→يهدف المشروع إلى بناء نظام محاسبي عربي يعمل **دون اتصال بالإنترنت بشكل أساسي (Offline-First بلا استثناء)**، يخزّن بياناته محلياً 100% في قاعدة **SQLite** على الجهاز عبر **expo-sqlite + Drizzle ORM**، مع تحقق مدخلات شامل بـ **zod**. النسخ الاحتياطي في V1 محلي بالكامل (ملف مضغوط يُشارك عبر النظام — واتساب/درايف)، والنسخ السحابي عبر Supabase خيار مؤجل إلى V1.1.
   154→
   155→اختير React Native + Expo لأنه يتيح تجربة التطبيق فوراً على الهاتف عبر Expo Go، وبناء APK سحابياً عبر EAS Build دون Android Studio، ومعاينة فورية أثناء التطوير عبر التصدير الثابت للويب من نفس الكود (قانون 0.4). التحليل الثابت للتطبيق المرجعي كشف أنه مبني بـ Flutter مع Firebase — وكل ميزة فيه قابلة للتنفيذ بمكافئات ناضجة في React Native (جدول الترجمة 3.4).
   156→
   157→**الخطة الزمنية المعتمدة (القسم 9)**: MVP بنهاية الأسبوع 8 (دورة بيع سليمة محاسبياً بالكامل)، **إصدار 1.0.0 في الأسبوع 13** لفرد واحد بدوام جزئي (3–4 ساعات/يوم)، والاتساع الكامل (الوحدات المؤجلة) بنهاية الأسبوع ~18 عبر إصدارات V1.1/V1.2.

   221→## 3. معمارية النظام المقترحة
   222→
   223→### 3.1 نظرة عامة — Offline-First بلا استثناء
   224→
   225→**القرار المعماري الجوهري: التطبيق يعمل محلياً أولاً — 100% من وظائف V1 بلا شبكة إطلاقاً** (قانون 0.3). قاعدة البيانات الأساسية هي SQLite على الجهاز نفسه، وكل الوظائف (فوترة، مخزون، تقارير، طباعة، نسخ) تعمل دون إنترنت. الإنترنت في V1 يُستخدم لوظيفة واحدة فقط: مشاركة ملفات PDF/النسخ عبر تطبيقات الجهاز (واتساب/درايف) — والمشاركة نفسها تتم عبر تطبيق الطرف الثالث المثبّت.
   226→
   227→هذا القرار مبني على ثلاث حقائق:
   228→1. **السوق اليمني** يعاني من انقطاع إنترنت متكرر، والتطبيقات المحاسبية هناك تعمل في محلات قد لا تملك إنترنت أصلاً.
   229→2. **الخصوصية**: بياناتك المالية تبقى على جهازك، ولا طرف ثالث يراها.
   230→3. **البساطة**: لا مصادقة سحابية ولا قواعد أمان شبكية — التطبيق شخصي بجهاز واحد ومدير واحد.

   257→### 3.2 قرار الخلفية السحابية — مؤجل إلى V1.1 (قرار نطاق)
   258→
   259→**قرار v1.2**: V1 **بلا أي خلفية سحابية** — التخزين محلي 100% والنسخ ملف مضغوط يُشارك عبر النظام (FR-11). هذا يزيل من مسار الإطلاق: حساب خارجي، تشفير نقل، فشل شبكة، وواجهة إعداد — شبكة الأمان الكافية للأسابيع الأولى هي النسخة المحلية + المشاركة.
   260→
   261→عند التنفيذ في V1.1، الخيار المعتمد **Supabase** (وليس Firebase): PostgreSQL يطابق عقلية SQLite المحلية، خطة مجانية تكفي لسنوات، مكتبة JS خالصة تعمل مع Expo فوراً، تصدير كامل بملكية كاملة للبيانات، والنسخ Snapshot كامل يرفع إلى Supabase Storage بعد تشفيره محلياً AES-256. (جدول المقارنة الكامل محفوظ في سجل المراجعة — ملحق ح.)

   263→### 3.3 قرار التنفيذ: قاعدة البيانات المحلية
   264→
   265→- **المحرّك**: `expo-sqlite` (Sync/Async API) مع **WAL مفعّل** دائماً.
   266→- **طبقة الاستعلام**: `drizzle-orm` مع مشغّل expo — تعريف المخطط بـ TypeScript، أنواع آمنة تلقائياً، هجرات مولّدة. **ممنوع Prisma** (قانون 0.3).
   267→- **التحقق**: كل عملية كتابة تمر عبر مخطط **zod** يقابل مخطط Drizzle (مستند، بند، حركة صندوق، إعداد) — الرفض قبل لمس القاعدة برسالة عربية مفهومة (قاعدة 6.3 لرسائل الخطأ).
   268→- **الترقيم**: عبر جدول `doc_sequence` بـ **UPSERT ذري** (لا `MAX+1` أبداً — القاعدة 5.4-1).
   269→- **التسمية**: أسماء الجداول بالإنجليزية snake_case، وكل النصوص الظاهرة بالعربية عبر `src/i18n/ar.ts`.
   270→- **الهجرات**: كل تغيير مخطط = ملف هجرة جديد في `drizzle/migrations/` مع تسجيل إصداره في `_migrations` — يسمح بترقية التطبيق دون فقدان البيانات. **الاستعادة من نسخة بمخطط أحدث من التطبيق تُرفض** برسالة واضحة (لا Downgrade).
